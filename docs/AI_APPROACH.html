01  The short answer

QuestionAnswer
Is there Python in this project?No. Everything is JavaScript — Node.js on the server, React in the browser.
Did we train a model?No. Nothing is trained. Nothing needs to be.
Is it a RAG system?Yes, genuinely. Retrieval and generation are both there, built from scratch.
Does it use an LLM?Optionally. It works with no API key at all; add a Gemini key and the answers read better.
Where does the “AI” live?server/src/rag/ — about 1,200 lines of hand-written retrieval, routing and answer composition.
Why no Python

Two reasons, both practical. The Python on this machine is 3.9, which is old enough that most current ML libraries fight it. And running a second language means a second process, a second set of dependencies, and a second thing that can be broken on demo day. One runtime that always starts beat a second runtime that sometimes doesn’t.

02  What RAG means, plainly

RAG stands for Retrieval-Augmented Generation. It’s a fix for the main problem with chatbots: they make things up.

A plain chatbot answers from whatever it absorbed during training. Ask it your college’s attendance rule and it will invent something that sounds right. RAG does it differently:

  1. Retrieval — first, go and find the relevant text in real documents.
  2. Augmented — hand that text to the answering step as the only material it may use.
  3. Generation — write the answer from that text, and say where it came from.

So the model is never asked “what is the attendance rule?”. It is asked “here are three passages from the college’s regulations — answer using only these”. That’s the whole idea, and it’s why every answer in this app carries a citation you can click.

03  The pipeline, step by step

Here is what happens between a faculty member uploading a PDF and a student getting an answer.

1
A document is uploaded
Faculty upload a circular, timetable, notes or slide deck, and tag it with the branch and semester it applies to.
server/src/routes/documents.js
2
Text is pulled out, format by format
PDFs, Word files, Excel sheets and PowerPoint decks are each read the right way — slide titles become headings, spreadsheet tables stay tables. Images are stored but not read (no OCR yet).
server/src/lib/parse.js
3
It’s cut into passages
About 700 characters each, split on whole sentences so a quote never starts mid-clause. Neighbouring passages overlap by one sentence, so a fact sitting on a boundary isn’t lost. Each passage remembers the heading it sat under — that’s what lets a citation say “§4.2 Attendance”.
server/src/rag/chunk.js
4
Words are normalised and indexed
Words are lowercased and stemmed (“attending”, “attended”, “attendance” all become one term), common words are dropped, and a small synonym table maps everyday phrasing onto document vocabulary — including a few Gujarati/Hindi transliterations like hajri and pariksha.
server/src/rag/tokenize.js · index.js
5
A question arrives — is it a lookup or a search?
“What’s my attendance?” is a database lookup. “What’s the attendance policy?” is a document search. Both contain the word “attendance”, so the router scores personal phrasing against policy phrasing to tell them apart.
server/src/rag/router.js
6
Permissions are applied before ranking
Passages the asker isn’t entitled to see are removed from the pool first, not filtered out of the results afterwards. A student can’t phrase a question cleverly enough to rank another branch’s material into view, because it was never in the running.
server/src/rag/retrieve.js
7
Passages are ranked with BM25
The standard text-search formula (the same family search engines have used for decades). Newer documents get a small boost, and material tagged for your own semester gets a small boost. At most two passages per document, so one circular can’t crowd out a second source.
server/src/rag/index.js · retrieve.js
8
Confidence is checked — and it may refuse
Two gates must both pass. If they don’t, it answers “not found in official documents” instead of guessing. See section 05.
server/src/rag/retrieve.js
9
The answer is written, with citations
Either by stitching the best sentences together (default, no internet needed) or by Gemini rewriting those same passages into prose. Citations are attached either way, as structured data the interface renders separately — so they can’t be hallucinated into the text.
server/src/rag/llm.js · answer.js

04  How the search works — and why not embeddings

There are two ways to find relevant text. This project uses the first one.

 Keyword search (BM25) — what we useSemantic search (embeddings)
How it worksMatches words, weighting rare words more heavily than common onesTurns text into a list of numbers capturing meaning, then finds the closest ones
NeedsNothing — pure arithmeticA trained model, a vector database
SpeedUnder a millisecondTens to hundreds of milliseconds
Handles rewordingPartly — via stemming and a synonym listYes, that’s the whole point
ExplainableYes — you can see exactly which words matchedNot really

BM25 was the right call for this corpus. College circulars are short, use consistent vocabulary, and students tend to ask using words that actually appear in them. The stemmer plus a hand-built synonym table covers most rephrasing — “how many lectures can I skip” finds the attendance rule even though the document says none of those words.

Its ceiling: a question phrased with genuinely no vocabulary in common with the document will miss. Embeddings would catch that. That’s the main thing Python would buy you — see section 08.

05  The part that matters most: refusing to answer

An assistant that invents an exam date is worse than no assistant. So before answering, two separate checks must both pass:

GateQuestion it asksThreshold
ScoreDid the best passage match well at all?2.2
CoverageWere the distinctive words of the question actually found?0.42

The second gate is the interesting one. Score alone is easy to fool: ask about the campus wifi password, and a hostel circular scores respectably purely because “campus” is a common word. So coverage weights each question word by how rare it is, and a word that appears nowhere in the corpus is charged the maximum penalty. A question the documents genuinely cannot answer sinks.

There’s an escape hatch for one real case: a single very rare, very precise match — like “unfair means” — is strong evidence even when the rest of the sentence is filler. That only counts if a second word corroborates it, so one coincidental rare word can’t carry an answer alone.

This is tested

npm run eval runs 26 cases: 22 routing decisions and 3 questions the documents deliberately can’t answer. All 26 pass. If you ever lower those thresholds to make a demo look better, that test is what will catch you.

06  Where the language model fits

Only at the last step — turning retrieved passages into a readable sentence. There are two modes, and the app picks automatically:

 Extractive (default)Gemini (optional)
Turned on byNothing — it’s the defaultSetting GEMINI_API_KEY
How it answersPicks and stitches the best sentences from the passagesRewrites those same passages into prose
Can it invent a fact?No — it can only quoteConstrained to the passages, and told to say NOT_FOUND if they don’t cover it
Reads likeQuotation — accurate but stiffNatural prose
Needs internetNoYes

Both return the same shape, so the rest of the app doesn’t know or care which ran. That was a deliberate rule: a feature that only works with an API key isn’t finished. If the wifi dies during your demo, the assistant keeps answering.

Turning Gemini on

Get a free key at aistudio.google.com/apikey, then put it in server/.env: 

GEMINI_API_KEY=your-key-here
GEMINI_MODEL=gemini-3.6-flash

Restart the server. Nothing else changes — same retrieval, same citations, better prose. This is the single highest-value five minutes you can spend on this project.

07  “Is this real AI?” — how to answer that

Yes, and here’s the honest framing.

A lot of student RAG projects are a thin wrapper: they send the user’s question straight to ChatGPT with some text pasted in front of it. The AI part is entirely somebody else’s API. Remove the key and there’s nothing left.

This one is the opposite. Everything that makes RAG work is written here:

  • the chunking strategy, including sentence-aligned splits and heading inheritance
  • the tokeniser, stemmer, stopword list and synonym mapping
  • the BM25 index and scorer
  • the intent router that separates record lookups from document questions
  • the scope filter that runs before ranking
  • the two-gate confidence check and the abstention behaviour
  • the extractive answer composer, with its weighting for obligations and numbers
  • the follow-up mechanism when a question is missing information

The LLM is one swappable component at the end. That’s the more defensible engineering position, and it’s worth saying plainly rather than apologising for the absence of a trained model. Nothing here needed training — the task is finding the right paragraph in fourteen documents, and BM25 does that better than a small fine-tuned model would.

08  Adding Python — three options

If you want Python in the project — because the syllabus expects it, or because it makes the report stronger — here are the three routes, cheapest first. All of them keep the existing Node app exactly as it is; Python is added alongside, never as a rewrite.

Option A · Python for OCR ~1–2 hours

What it fixes: handwritten notes and photographed circulars are stored and downloadable today, but the assistant can’t read them. This is a real, documented gap — not invented work.

How: a tiny Python service that accepts an image and returns text.

pip install fastapi uvicorn pytesseract pillow
# plus: brew install tesseract

Node calls it at http://localhost:8000/ocr when an uploaded file is an image, and the text it returns goes through the same chunking and indexing as everything else. Roughly 40 lines of Python and one if in parse.js.

Why it’s first: smallest change, closes a gap you’ve already documented, and demos well — upload a photo of a handwritten notice, then ask about it.

Option B · Python for semantic search ~3–4 hours · best result

What it fixes: the real ceiling from section 04 — questions phrased with no words in common with the document.

How: a Python service that turns text into embeddings.

pip install fastapi uvicorn sentence-transformers
# model: all-MiniLM-L6-v2 — 80MB, runs on a laptop CPU
  1. On upload, Node sends each passage to Python and stores the returned vector in MongoDB alongside the passage.
  2. On a question, Node sends the question to Python, gets a vector, and finds the closest passages.
  3. Combine both lists — BM25’s and the vector search’s — with reciprocal rank fusion. Keep the existing abstention gate on top.
Don’t replace BM25 — fuse with it

Hybrid search beats either method alone, and it’s the current standard practice. It’s also safer: if the Python service is down, you fall back to BM25 and the app still works. Re-run npm run eval afterwards and do not accept a drop in the abstention score to buy accuracy elsewhere.

Bonus: MongoDB Atlas has vector search built in on the free tier, so you don’t need a separate vector database. Python just produces the numbers.

Option C · Rewrite the RAG layer in Python ~2–3 days · not recommended

Move all of server/src/rag/ to a Python FastAPI service, probably using LangChain or LlamaIndex.

Why I’d push back:

  • You’d be rebuilding something that already works and passes 26 tests.
  • LangChain would replace your hand-written retrieval with a library call — which makes the project less impressive, not more. The custom retrieval is the strongest part of this codebase.
  • Two processes to start means twice as many ways for the demo to fail.

Only worth it if someone has explicitly told you the AI component must be written in Python.

09  What I’d actually do

In this order:

  1. Set GEMINI_API_KEY. Five minutes, free, and it’s the biggest visible improvement available. Do this regardless of the Python question.
  2. If Python is required: Option A first (OCR). It’s genuinely useful, it’s quick, and it gives you a real Python component to write about.
  3. If you have a spare afternoon and want the strongest version: Option B (hybrid search). This is the one that would impress someone who knows the field.
  4. Skip Option C unless it’s mandated.

Say the word and I’ll build whichever of these you pick.

10  If you’re asked in a viva

“Where is the AI in this project?”

It’s a retrieval-augmented generation system. Retrieval is a BM25 index built from scratch over passages we chunk out of the college’s own documents; generation composes an answer strictly from those passages and cites them. The retrieval, ranking, routing and abstention logic is all ours — the language model is one swappable component at the end, and the system works without it.

“Why didn’t you train a model?”

The task is finding the right paragraph in a set of college documents, not learning a new skill. Training would need labelled data we don’t have, and would be worse at it. RAG is the correct architecture for grounded question answering over a document set that changes every time a circular is issued — and retraining on every new circular would be absurd.

“What happens if it doesn’t know?”

It says so. Two confidence gates — a relevance score and an IDF-weighted coverage check — must both pass, otherwise it returns “not found in official documents”. That behaviour is tested: three of the 26 eval cases are questions the corpus deliberately cannot answer, and it abstains on all three.

“Why JavaScript and not Python?”

One runtime for the whole system — fewer moving parts, one deployment, and the retrieval layer needed no ML library. If we add semantic search, that’s where Python earns its place: a small embedding service fused with BM25 rather than replacing it.

“What’s the weakest part?”

Lexical retrieval will miss a question that shares no vocabulary with the document. And there’s no OCR, so handwritten material is stored but not searchable. Both are known, both are documented in docs/PROJECT_STATE.md, and both have a planned fix.

Knowing your own limitations is worth marks

Every honest answer above is stronger than a vague one. “Here’s exactly where it breaks, here’s the fix, here’s why we didn’t do it yet” reads as engineering judgment. Claiming it handles everything reads as not having tested it.
