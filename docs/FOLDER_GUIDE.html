The API the frontend talks to. It handles login, stores and returns records, and runs the chatbot.

src/rag/ · the chatbot brain

answer.jsOrchestrator. ask() runs the pipeline: check for missing details, then classify the intent, then look up a record or search documents, then write the answer with citations.
router.jsIntent detection. It decides whether a question needs a record lookup ("my attendance") or a document search ("attendance policy").
structured.jsAnswers record questions (timetable, attendance, results) straight from the database.
retrieve.jsDocument search with role filtering, newest version only, and the confidence gate that refuses to guess (MIN_SCORE, MIN_COVERAGE).
index.jsThe in-memory BM25 search index over document passages. It is rebuilt when documents change.
chunk.jsSplits document text into passages of about 700 characters, made of whole sentences with one sentence of overlap. It also tags each passage with its section heading.
tokenize.jsTurns text into search words: drops stopwords and maps synonyms together (e.g. "CGPA" and "CPI"). The index and the query use the same rules.
llm.jsAI adapter. The default is extractive (offline, quotes sentences only). With GEMINI_API_KEY it uses Gemini. providerStatus() reports which one is active.
generate.jsBuilds question-bank drafts from uploaded material, across Bloom's levels. Always saved as a draft.
enrich.jsOptional background step after an upload (Gemini only). It reads scanned files and writes a summary, topics and tags.
suggest.jsSuggestions while typing (e.g. "exam" brings up exam actions), filtered by role.
__eval__.jsTest set of 26 cases for routing, citations and refusals (npm run eval).

src/seed/ · demo data

seed.jsWipes and regenerates all demo data: users, subjects, timetable, attendance, results, documents (npm run seed). It uses a fixed random seed, so every run gives the same data.
catalogue.jsSubject list per branch (CE, IT, ME) and semester (1–8), plus faculty and student names.
corpus.jsThe demo policy documents (attendance rules, exams, etc.) the chatbot searches.

data/ · storage (not committed to Git)

*.jsonOne file per collection: users, subjects, timetable, attendance, results, documents, chunks, assignments, submissions, announcements, questionbanks, conversations. Used when MongoDB is not available.

flows

How the pieces connect

A student asks a question

  1. pages/Assistant.jsx sends it through lib/api.js to POST /api/chat/ask.
  2. routes/chat.js checks the token and works out who is asking (scopeOf).
  3. rag/answer.js: if a detail is missing (e.g. semester), it asks a follow-up question instead of guessing.
  4. rag/router.js classifies the question as a record question or a document question.
  5. Record questions go to rag/structured.js, which reads the database.
    Document questions go to rag/retrieve.js, which runs a BM25 search via rag/index.js.
  6. If confidence is too low, the reply is "not found in official documents".
  7. rag/llm.js writes the answer (extractive or Gemini) and attaches the citations.

Staff upload a document

  1. pages/Library.jsx sends the file to POST /api/documents.
  2. multer saves it to server/data/uploads/.
  3. lib/parse.js extracts the text, and rag/chunk.js splits it into passages that are stored in the database.
  4. The search index rebuilds, so the document can be searched straight away.
  5. If a Gemini key is set, rag/enrich.js summarises the document in the background.
viva

Quick answers

What is RAG?
Retrieval-Augmented Generation. The system first finds relevant passages in official documents, then answers only from them, with a citation.
Which search algorithm do you use?
BM25, written in plain JavaScript (server/src/rag/index.js). It needs no API key or internet.
How does it avoid wrong answers?
A confidence gate in retrieve.js checks two things: the BM25 score, and how many of the question's important words were found. If either is too low, it says "not found" instead of guessing.
How does it tell "my attendance" from "attendance policy"?
router.js looks for personal words (my, I, me) versus policy words (rule, policy, minimum). The first is a record lookup, the second is a document search.
Where is the data stored?
MongoDB. If MongoDB is not available, the same data is read from JSON files in server/data/. Only db.js knows which one is in use.
Does it need an AI key?
No. By default it works offline and quotes sentences from documents. A Gemini key is optional and makes answers more fluent. Without the key it falls back to offline mode and reports that it did.
How is security handled?
bcrypt-hashed passwords, JWT login tokens, and role checks on the server (requireRole). A student can only see their own records, because the ID comes from the token, not from the request.
What are the three roles?
Student (views own data, asks questions), Faculty (marks attendance, grades, uploads, makes question banks), Admin (everything, plus users and subjects).
How do frontend and backend talk?
Through a REST API under /api. All calls go through web/src/lib/api.js. In development, Vite proxies /api to port 4000.
What file types can be uploaded?
PDF, Word, Excel/CSV, PowerPoint, text and images, up to 25 MB (lib/parse.js).
Why no UI library or chart library?
The design is small and custom, so hand-written CSS and SVG match it exactly and keep the app light.
How did you test it?
npm run eval runs 26 retrieval, routing and refusal cases. npm run smoke runs end-to-end API checks for all three roles.
Where does the demo data come from?
server/src/seed/seed.js generates realistic sample data. Real college records are private, so none were used.
How do I run it?
npm install, then npm run dev. The frontend is at localhost:5173 and the API at localhost:4000. Demo password: demo1234.
