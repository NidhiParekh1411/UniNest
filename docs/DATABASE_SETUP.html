Setup guide

Connecting the app to a real MongoDB database

The app runs right now with no database at all — skip to the green box below if you just want to see it. This guide is for when you want a real one: a free cloud database on MongoDB Atlas. It takes about fifteen minutes and costs nothing.

You do not need any of this to run the app

If MongoDB is not reachable, the server automatically loads the JSON files in server/data/ instead, and prints a line saying so. So this works today, from a fresh clone, with nothing installed: 

npm install
npm run dev

Open localhost:5173 and sign in with the one-tap demo accounts. Everything works — the assistant, uploads, grading, notices — and your changes are saved back to those JSON files.

So why bother with Atlas? Because the file store keeps everything in memory in one process. It cannot be shared between two machines, it will not survive being deployed anywhere real, and two processes writing at once will fight. It is the right answer for developing and demoing, and the wrong answer for anything else.

01  What you actually need to do

Good news first: you do not need to create any tables or collections. MongoDB creates them automatically the first time something is written, and the project already has a script that builds every collection, adds the indexes, and fills them with demo data.

So the entire job is three things:

  1. Get a database in the cloud (free).
  2. Copy one line — its connection address — into a file in the project.
  3. Run npm run seed.
How the server picks a store

On startup it tries MongoDB for three seconds. If that works it uses it; if not it falls back to the JSON files and warns you. The line it prints tells you which one you got — check it if data isn’t appearing where you expect.

You can force the choice with DB_DRIVER in server/.env: file to always use JSON, mongo to require a database and fail loudly without one. Leave it blank for the automatic behaviour.

02  Create the free cluster

1

Go to mongodb.com/cloud/atlas/register and sign up. Google sign-in is fastest.

2

When it asks what you’re building, pick anything — it only changes the tips it shows you.

3

On the “Deploy your cluster” screen choose the M0 / Free tier. Make sure it says Free and $0.00/month before you continue.

For the region, pick Mumbai (ap-south-1) — it’s the closest to Ahmedabad, so the app will feel faster.

4

Give the cluster a name — campus-assistant works — and click Create Deployment. It takes a minute or two to finish building.

Don’t add a credit card

The M0 tier never asks for one. If a screen wants payment details, you’ve picked a paid tier — go back and choose M0.

03  Create a database user

This is the username and password the app uses to talk to the database. It is not your Atlas login.

1

Atlas usually shows this right after the cluster is created. If not, click Database Access in the left sidebar, then Add New Database User.

2

Username: campusapp

Password: click Autogenerate Secure Password, then copy it somewhere safe right now. You cannot see it again later.

3

Under privileges choose Read and write to any database, then Add User.

If your password has symbols in it

Characters like @ : / ? # break the connection address. Save yourself the trouble: use the autogenerated password, or make one with only letters and numbers.

04  Allow your computer to connect

Atlas blocks everything by default. You have to say which computers are allowed in.

1

Click Network Access in the left sidebar, then Add IP Address.

2

Click Allow Access from Anywhere. It fills in 0.0.0.0/0. Confirm.

This means “any computer with the password can connect”. For a college project that is the right call — otherwise you’ll re-add your IP every time you move between home wifi and campus wifi.

Is that safe?

For a demo with generated sample data, yes — the password is still required. For anything with real student records, you would restrict it to specific addresses instead. Worth saying out loud if anyone asks you about it.

05  Get the connection string

1

Click Database in the sidebar, then the Connect button on your cluster.

2

Choose Drivers. Driver: Node.js. Version: whatever it suggests.

3

Copy the address it shows. It looks like this:

mongodb+srv://campusapp:<db_password>@campus-assistant.ab1cd.mongodb.net/?retryWrites=true&w=majority

Replace <db_password> — including the angle brackets — with the password you saved in step 03.

06  Put it into the project

Open server/.env in your editor. Find the MONGODB_URI line and replace it with your address:

# server/.env
PORT=4000
JWT_SECRET=change-me-in-production

MONGODB_URI=mongodb+srv://campusapp:YourRealPassword@campus-assistant.ab1cd.mongodb.net/?retryWrites=true&w=majority
MONGODB_DB=college_rag

# Optional — see the AI document
GEMINI_API_KEY=
GEMINI_MODEL=gemini-3.6-flash
Three things to check

No spaces around the =. No quotes around the address. The password is the real one, not <db_password>.

MONGODB_DB is the name of the database inside the cluster. Leave it as college_rag — the app creates it for you.

07  Fill the database with data

From the project folder, run:

npm install
npm run seed

You should see it print what it created, and the demo logins at the end. This one command:

  • creates all twelve collections
  • adds the indexes that make lookups fast
  • generates 72 students, 16 faculty, 117 subjects, timetables, attendance, results, assignments, documents and notices
  • prints the demo accounts you can sign in with
This wipes everything first

npm run seed empties every collection before it writes. That’s intentional — it means you can always get back to a clean demo. Just don’t run it against a database holding anything you want to keep.

09  What the collections hold

You don’t create these — npm run seed does. This is here so you know what’s in your database when you open Atlas and look, and so you can answer questions about it.

A quick translation if you’re used to SQL: a collection is a table, a document is a row. The difference is that documents don’t all have to have the same columns.

CollectionWhat’s in itRoughly
usersStudents, faculty and admins — name, email, hashed password, role, branch, semester89
subjectsEvery subject, its code, credits, and which faculty teaches it117
timetableOne row per class slot — day, time, room, lecture or lab466
attendancePer student, per subject: classes held and classes attended360
resultsMarks per student, per subject, per exam type1,800
documentsUploaded circulars, notes and timetables — the file’s details, not the file itself14
chunksThose documents cut into searchable passages. This is what the assistant searches.69
assignmentsWork set by faculty, with due dates45
submissionsWhat students handed in, grades and feedback143
announcementsNotices, including ones scheduled for later10
questionbanksGenerated question papers awaiting faculty approval—
conversationsChat history with the assistant—

The actual uploaded files (PDFs, images) stay on disk in server/data/uploads/. Only their details go in the database. That’s deliberate — a 25 MB PDF inside a database row causes problems that a file on disk doesn’t.

Want to look inside?

In Atlas click Database → Browse Collections. You can read and edit any row from the browser. Handy for a demo — change a student’s attendance there and refresh the app to show it update live.

10  What I do once you’re done

Message me when npm run dev starts cleanly. Then I’ll work through this list:

  • Verify it end to end. Run npm run smoke and npm run eval against your live cluster and fix anything that fails.
  • Check the new UI in a real browser at 375px, 768px and 1440px. It’s been built to the design system but not yet seen running — that gap needs closing.
  • Build attendance marking and result entry screens. The API endpoints already exist and are tested; there’s just no screen calling them. This is the single biggest “this is a demo” gap left, and it’s pure UI work.
  • Add bulk import from Excel for timetables, attendance and results — the spreadsheet parser already returns structured tables, nothing consumes them yet.
  • Wrap the delete-document path in a transaction. Deleting a document removes its passages in a second call; a crash in between leaves orphans. Atlas supports transactions, the local setup didn’t.
  • Add a proper loading and error state for a slow cloud connection — Atlas is milliseconds away, not microseconds, and some screens assume the latter.

If you want a different order, tell me — the attendance and result entry screens are the ones an examiner is most likely to ask about, so I’d start there.

11  If something goes wrong

What you seeWhat it means
bad auth / Authentication failed Wrong username or password in the address. Most often, <db_password> was never replaced, or the password has a symbol in it. Reset the password in Database Access to letters and numbers only.
querySrv ENOTFOUND The cluster address is wrong or mistyped. Copy it again from Connect → Drivers.
It hangs, then ServerSelectionTimeout Your IP isn’t allowed. Go to Network Access and add 0.0.0.0/0. Also happens on a network that blocks port 27017 — some college wifi does; try a phone hotspot to check.
Set MONGODB_URI in server/.env The app can’t see your setting. Check the file is server/.env and not server/.env.example, and that you saved it.
App runs but every page is empty You connected to Atlas but never seeded. Run npm run seed.
Changes vanish, or data looks stale You ran npm run seed while npm run dev was still running in file mode. The server holds the data in memory and the seed rewrote the files underneath it. It detects this and reloads rather than corrupting anything — but stop the server before seeding, then start it again.
Not sure which store you’re on Read the startup line: it says either store: MongoDB · college_rag or store: local files (server/data).
Sign-in says “invalid credentials” Use the one-tap demo buttons rather than typing. If they’re missing, the API isn’t reachable — check the terminal running npm run dev.
Never commit your password

server/.env is already in .gitignore, so it won’t be uploaded if you push this to GitHub. Don’t paste the connection string into a report, a slide, or a screenshot either.
