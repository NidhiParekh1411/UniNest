1. The shape of the problem

UniNest is two programs that have to run together. The frontend is a React app that Vite compiles into plain files. The backend is a Node process that answers /api/…, signs JWTs, accepts file uploads, parses PDFs and talks to MongoDB. Right now they are stitched together only in development, by the proxy in web/vite.config.js: 

proxy: {
  '/api': { target: 'http://localhost:4000', changeOrigin: true },
}

That proxy is the reason web/src/lib/api.js can write fetch(`/api${path}`) with no host in front of it. The proxy exists only when npm run dev is running. In production, something else has to make /api/… resolve — and the cheapest, least invasive answer is to have the Express process serve the built frontend itself.

2. Why GitHub Pages alone cannot host this

GitHub Pages serves static files. It has no way to run a Node process, so it cannot run Express, cannot hold a JWT secret, cannot accept an upload and cannot reach MongoDB. If you deployed web/dist to Pages and nothing else, the login screen would render perfectly and every single request behind it would fail.

So GitHub keeps doing what it already does well — hold the source, and trigger the deploy on push. The running app lives on a host that can execute Node. The free options that fit are Render, Railway and Fly.io; this document assumes Render, because its free tier needs no card and it reads the engines field already declared in package.json.

3. The plan in one paragraph

One service, one URL, no cost

Express serves both the API and the built React app, so the whole thing is a single origin at a single address. api.js keeps using relative URLs and needs no edit. There is no CORS to configure, no second deployment to keep in sync, and no base-URL environment variable to get wrong. The data lives in a free MongoDB Atlas cluster. Render rebuilds and redeploys automatically every time you push to the chosen branch.

4. The six code changes

Every one of these is mine to make. They are listed in the order I would apply them, on the v2 branch, as described in CLAUDE.md.

Serve the built frontend from Express

I do this
server/src/index.js

The problem. index.js mounts nine /api/* routers and then a catch-all that 404s anything else under /api. It never serves an HTML page. Deployed as-is, the root URL returns nothing and visitors see a blank screen.

The change. After the API routes and before the error middleware, serve web/dist statically and send index.html for any path the API did not claim — so a deep link like /faculty/assignments and a browser refresh both resolve through React Router instead of 404ing: 

// In production the API also serves the built frontend, so the whole app is
// one origin: api.js fetches "/api/…" relative, exactly as it does behind the
// Vite dev proxy. Nothing in web/ needs a base URL.
const CLIENT_DIR = path.resolve(__dirname, '../../web/dist');
if (fs.existsSync(CLIENT_DIR)) {
  app.use(express.static(CLIENT_DIR));
  // Anything not matched above is a client route — hand it index.html
  // and let the router resolve it.
  app.get('*', (_req, res) => res.sendFile(path.join(CLIENT_DIR, 'index.html')));
}

The existsSync guard matters: dist/ is gitignored and does not exist until something runs npm run build, so in local development this block simply does not activate and the Vite proxy keeps working exactly as it does today. Nothing about your current workflow changes.

Stop accepting requests from every origin on the internet

I do this
server/src/index.js

The problem. app.use(cors()) with no arguments allows any website anywhere to call your API. That is harmless on localhost and careless on a public URL.

The change. Because the frontend will be served from the same origin as the API, cross-origin access is not needed at all in production. CORS becomes opt-in through an environment variable, and stays wide open in development so nothing about local work changes: 

// Same-origin in production (Express serves web/dist), so CORS is only
// needed for the split dev setup or an explicitly allowed external origin.
const ORIGIN = process.env.CORS_ORIGIN?.trim();
if (ORIGIN) app.use(cors({ origin: ORIGIN.split(',').map((s) => s.trim()) }));
else if (process.env.NODE_ENV !== 'production') app.use(cors());

Refuse to start in production with the default JWT secret

I do this …and you set the secret
server/src/lib/auth.js
This is the one genuinely dangerous item

auth.js:10 reads process.env.JWT_SECRET || 'dev-only-secret-change-me'. That fallback string is in a public repository. If the deployed app ever runs without JWT_SECRET set, anyone who has read your source can mint themselves a valid admin token and sign in as anybody.

The change. Keep the convenient fallback for local development, but make it a fatal startup error in production. A deploy that would have been silently insecure instead fails loudly with one line telling you what to set: 

const SECRET = process.env.JWT_SECRET || 'dev-only-secret-change-me';

// The fallback is public — it is in the repo. Signing real sessions with it
// would let anyone forge an admin token, so refuse to run that way.
if (process.env.NODE_ENV === 'production' && !process.env.JWT_SECRET) {
  throw new Error('JWT_SECRET must be set in production — see docs/DEPLOYMENT.html');
}

Make the upload directory configurable

I do this
server/src/lib/db.js

The problem. db.js:22 pins uploads to server/data/uploads, inside the deployed code directory. On Render’s free tier that directory is wiped on every restart and every redeploy, so uploaded documents quietly disappear. The database rows survive; the files they point at do not.

The change. One line, so the directory can be pointed at a mounted disk later without touching code: 

export const UPLOAD_DIR = process.env.UPLOAD_DIR
  ? path.resolve(process.env.UPLOAD_DIR)
  : path.join(DATA_DIR, 'uploads');

With UPLOAD_DIR unset, behaviour is identical to today. See section 8 for what this does and does not solve on a free plan.

Add a root start script

I do this
package.json

The root package.json has dev, seed, build and others, but no start. Hosting platforms look for exactly that by default. Adding it means the Render setup form needs no custom command: 

"start": "npm start -w server"

engines.node is already >=20, and index.js already reads process.env.PORT — so Render’s assigned port and Node version are both handled without further work.

Document the deployment and update the handoff file

I do this
README.md · docs/PROJECT_STATE.md · server/.env.example

A public repo that other people are meant to use needs the live URL and the demo logins in the README, and .env.example needs the three new variables described below. 5. Environment variables

These go into Render’s Environment tab — never into a file in the repo. server/.env is gitignored and stays on your machine only.

VariableValueWhy
NODE_ENV production Switches off dev CORS and arms the JWT secret check
JWT_SECRET a long random string Signs sessions. Generate with openssl rand -base64 32
DB_DRIVER file Set by render.yaml. Switch to mongo when you add Atlas
MONGODB_URI your Atlas SRV string Only when DB_DRIVER=mongo
MONGODB_DB college_rag Only when DB_DRIVER=mongo
GEMINI_API_KEY optional Upgrades answer synthesis. Without it the offline extractive path is used
Why the build command runs the seed

.gitignore excludes server/data/*.json, so the repository ships no data. A deployment that skipped the seed would start happily with zero users — every login returning “Those credentials do not match an account”, and the one-tap demo buttons gone because /api/auth/demo-accounts returns an empty list. It looks exactly like an authentication bug and it is not one.

render.yaml therefore ends its build with DB_DRIVER=file npm run seed, which writes the full demo dataset into the container. That is what lets this deploy with no database account at all.

6. What you need to do

Four things, roughly ten minutes, no card and no database account required. Everything here involves an account or a secret, which is why it cannot be mine.

1

Confirm you can push to the repo

origin is github.com/NidhiParekh1411/UniNest, and git here is configured as Nidhi Parekh. If that is not your own account, you need collaborator rights on it before any of this reaches GitHub. Tell me which account should own the deploy.

2

Import the repo on Render

Sign in to render.com with GitHub, choose New → Blueprint, and pick the UniNest repo. Render reads render.yaml from the branch and fills in the build command, the start command, the health check and the environment — including a freshly generated JWT_SECRET it never shows anyone.

The only thing to choose is the branch. There are no fields to fill in and no secrets to paste.

3

Add the Gemini key, if you want the better answers

Optional. In Render’s Environment tab add GEMINI_API_KEY. Without it the assistant uses the offline extractive path — still correct, still cited, just blunter, and the record lookups below work either way. Do not paste the key into a chat, a report, a slide or a screenshot.

4

Open the URL and check three things

  • The sign-in screen shows the one-tap demo buttons — if it does not, the API is reaching an empty store
  • Signing in as the student lands on a dashboard with real data, not empty states
  • Refreshing the page on an inner route still works — that is the SPA fallback from change 1

Send me anything that misbehaves and I will fix it from here.

8. What will still be imperfect

Worth knowing before you share the link with anyone.

LimitationEffectFix if it matters
Free instances sleep when idle The first visit after a quiet period takes roughly a minute to respond while the container wakes A paid instance, or a scheduled ping. For a demo, just open the link a minute before showing it
Uploaded files are not persistent Documents uploaded through the app vanish on restart or redeploy; their database records remain and point at nothing Attach a Render persistent disk and set UPLOAD_DIR to it (change 4 makes this a settings change, not a code change)
Anyone with the link can sign in The demo accounts are public knowledge — they are printed in the docs Fine while the data is seeded demo data. Before any real student record goes in, the demo accounts must go

9. If something goes wrong

SymptomAlmost certainly
Blank white page at the root URL The build did not run, so web/dist is absent and the static block in change 1 skipped itself. Check the build command
Login fails and the demo buttons are missing The app is in file mode against an empty store. DB_DRIVER is unset, or the Atlas URI is wrong
Deploy fails immediately with a JWT message Working as designed — JWT_SECRET is not set. Change 3 caught it
Atlas connection times out Network Access is not open to 0.0.0.0/0, or the password in the URI is not URL-encoded
Inner routes 404 on refresh but work when clicked The SPA fallback is not reached — usually a route mounted after it. Tell me and I will reorder
Uploads succeed, then the file is gone tomorrow Expected on free hosting. See section 8
