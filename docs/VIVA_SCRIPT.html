How we built UniNest

A college assistant that answers student questions from the college's own documents — and says "not found in official documents" instead of guessing. Built by a team of two. This page walks the six phases in order, with the actual decisions we took and the reason for each one.

01
Phase one

Gathering the requirements

What we did

  • We started from a problem statement deck given to us (reference/college_rag_assistant_presentation.pptx). Both of us read it separately, then compared notes.
  • The core problem: student information is scattered across circulars, timetables, syllabi and policy PDFs. There is no single place to search. Documents get revised, so even the right PDF can be out of date. The same questions keep landing on faculty and admin.
  • We asked questions back rather than assuming. The answers changed the design: Do students in different semesters see different timetables? (Yes.) Does one faculty member teach across semesters? (Yes.) Should admin and faculty share a login screen? (Yes — but students get their own.) Can a student upload handwritten work? (Yes.)
  • We wrote everything down in docs/REQUIREMENTS.md, split into functional (what it must do) and non-functional (how it must feel and perform), so nobody had to reopen the deck again.
  • We also recorded the questions we could not answer yet — six of them, like "should this plug into the existing college portal?" — as open items rather than pretending we had decided.
Say this

"We didn't just take the deck at face value. We turned it into a written requirements document, separated what the system must do from how it must behave, and kept a list of open questions we deliberately deferred instead of guessing at."

02
Phase two

Analysis and feasibility

What we checked first

  • What already exists: colleges already have ERP portals, but they store records — they do not answer questions from documents. That gap is our project.
  • What is actually feasible for us: the deck proposed one stack. We tested it on our own machines before committing, and changed parts of it. That is the most important thing in this phase.
  • What to keep and what to drop: we scoped a Phase 1 that is complete and demo-ready, and wrote the rest down as known, deliberate gaps in docs/PROJECT_STATE.md rather than leaving them as loose ends.

The technical decisions, and why

DecisionWhat we choseWhy
Backend language Node.js 20 + Express, not Python The Python on our machines was 3.9.1. The ML libraries the deck suggested were slow and kept failing to install. Node gave us one runtime for both frontend and backend, and it installed cleanly.
AI provider Google Gemini, free tier It has a genuinely free tier and does not need a credit card. We put it behind an adapter (src/rag/llm.js) so it can be swapped without touching the rest of the code.
Working without a key Offline extractive fallback The free tier is capped per day. If the quota runs out mid-demo, the app must not break — it drops to answering with the retrieved text itself, and it tells you it downgraded.
Search / retrieval BM25 in plain JavaScript The deck wanted sentence-transformer embeddings and a vector database. That needs Python, a model download and a server. BM25 is a proven keyword-ranking algorithm that runs with zero API keys and no network — so the demo always works.
Database MongoDB Our records are document-shaped and the fields differ by role. Mongo fit that without migrations. We also wrote a JSON-file fallback so a fresh clone runs with no database at all.
Charts Hand-written SVG A charting library would have brought its own look. We wanted the charts to match our design exactly, with no extra dependency.

Designing the database and its test data

  • We listed every collection (Mongo's version of a table) straight from the requirements — users, subjects, timetable, attendance, results, documents, chunks, assignments, submissions, announcements, questionbanks, conversations. Twelve in total.
  • Every record keeps its own readable id (usr_stu009, sub_CE5_3150703) instead of relying on Mongo's internal _id. That means ids stay the same when we regenerate the data.
  • We added indexes based on the queries we actually wrote — for example attendance is indexed on studentId, because that is how every attendance screen reads it.
  • Real student records are private, so we could not use real data. We wrote a seed script (server/src/seed/seed.js) that generates realistic demo data in exactly the shape real records will take, so a college can drop its own data in later.
  • The seed uses a fixed random seed, so it produces the same data every time. A demo never looks different twice. Running npm run seed gives us 16 faculty, 72 students, 117 subjects, 466 timetable entries, 1,800 results and 14 indexed documents.
  • All database access goes through one file, server/src/lib/db.js. No route or AI module talks to Mongo directly — that is how we kept the file-based fallback possible at all.
Say this

"We deliberately deviated from the suggested stack after testing it. Python 3.9 on our machines made the ML dependencies fragile, so we moved to Node. And instead of a vector database we used BM25, which means the whole assistant runs with no API key and no internet — the demo can never fail because a quota ran out."

03
Phase three

Design

How we decided what it should look like

  • Neither of us is a designer, so we researched instead of guessing. We searched for college dashboards and student portals, and browsed Dribbble for layout ideas.
  • We screenshotted everything we liked and saved it into the repo as screenshots/college_ref(1) through (11). These became the reference we designed against — not a vague memory of "something clean".
  • Our first version used the theme from the original brief: white background, black text, and an orange-to-pink gradient. When we looked at it on screen we did not like it — the gradient was everywhere and every card looked the same.
  • So we rebuilt the visual system from our reference screenshots: a warm-grey page (#F5F5F4), white blocks, near-black text, and four soft pastels — lime, sky, lavender and peach.
  • We gave each colour one job. Sky always means a document or citation. Lavender always means a lab. Lime marks the selected or active thing. Peach means "needs attention". A colour never just decorates.
  • One typeface — Manrope. Hierarchy comes from weight and size, not from mixing fonts.
  • We wrote all of this into web/src/styles/theme.css as design tokens, and made a rule: a hard-coded colour anywhere else in the code counts as a bug.
  • Mobile was designed first, then widened — every screen is checked at 375px, 768px and 1440px.
Say this

"We collected reference screenshots before writing any CSS, and we kept them in the repo. Our first theme came from the brief, but when we saw it running we rejected it and rebuilt the system around flat pastel blocks — where each colour carries a fixed meaning rather than being decoration."

04
Phase four

Setting up AI-assisted development

The idea

  • We used an AI coding assistant to build this. But an AI assistant with no rules produces inconsistent code — a different colour on every screen, a new pattern in every file.
  • So before writing application code, we spent time writing the rules the AI had to follow. This is the part of our process we think is genuinely different, and it is worth showing.

The files we wrote first

FileWhat it does
CLAUDE.md The project rulebook, read at the start of every session. It holds the stack table with the reason for each choice, a map of the repo, and seven house rules — design tokens only, mobile is not an afterthought, all data access through db.js, role scoping is enforced on the server, the assistant must never guess, every AI path must degrade and say so, and keep the state file current.
.claude/skills/ui-guide/ The design system as a loadable skill: the palette, the type scale, the spacing tokens, and a section called "the rules that get broken most" — for example lime is a background, never text, because on white it only has 1.3:1 contrast.
.claude/agents/ui-builder.md A specialist for frontend work. It is required to load the design system before writing a single line of a component.
.claude/agents/rag-engineer.md A specialist for the AI and retrieval layer. Its brief states the non-negotiable: grounded answers with citations, and an honest "not found" when confidence is low.
docs/PROJECT_STATE.md The handoff file. At the end of every working session we update what is done, what is deliberately not done, and where we stopped — so the next session starts with full context.

Why this mattered

  • We gave the AI constraints, golden examples and reference screenshots up front, instead of correcting it afterwards.
  • Some rules exist because we hit the bug once and wrote it down so it could not happen again — for example, a CSS mask reads transparency, not colour, and writing it the wrong way silently erased the middle of a scrolling row. That bug is now documented in the guide.
  • The result is that eleven screens built over several sessions still look like one product.
Say this

"Before we built any feature, we built the guardrails. We wrote a project rulebook, a design-system skill and two specialist agent briefs, so the AI worked inside our constraints instead of inventing its own. Reviewing AI output against written rules is much faster than reviewing it against taste."

05
Phase five

Building it, screen by screen

The order we worked in, and why

  • Landing page first. It sets the visual language — colours, spacing, typography — with no logic in the way. Once it looked right, every later screen had something to copy.
  • Authentication second. Nothing else can be built properly until the app knows who is asking. We used JWT tokens signed with HS256, plus role-checking middleware.
  • We built two sign-in screens — students on one, faculty and admin sharing the other, as the brief asked. Using a student account on the staff screen is refused with a clear message rather than a generic error.
  • Then the tabs, one at a time: Dashboard → Assistant → Timetable → Attendance → Results → Assignments → Library → Notices → Question banks → People → Subjects.
  • Each tab followed the same loop: build it mobile-first, wire it to a real API route, check it at three screen widths, then move on.

The two rules we never broke

  • Security is enforced on the server, not in the interface. Hiding a button is not security. Every route that returns student data filters by the identity inside the token — never by an id sent in the request. So a student cannot read another student's attendance even by editing the request by hand.
  • The assistant must never guess. If the retrieval score is below threshold, it answers "not found in official documents". Any answer drawn from a document must carry a citation naming that document and section. This came straight from the problem statement and it is the core promise of the product.
Say this

"We built the landing page first to lock the visual language, then authentication, because every other screen depends on knowing who is asking. Role scoping is enforced server-side on every route — the UI hiding a button is not security."

06
Phase six

Testing, review and fixing

How we tested

  • We reviewed it on screen, together. Several rounds. Most of our real bugs were found by looking at the running app, not by reading code.
  • We tested the AI's honesty deliberately. We asked questions the documents cannot answer, to confirm it says "not found" instead of inventing something. We also tested the pair "what is my attendance" versus "what is the attendance policy" — one is a record lookup, the other is a document question, and the router has to tell them apart.
  • We tested each role separately, checking that a student, a faculty member and an admin each see only what they should.
  • We checked every screen at 375px, 768px and 1440px, and confirmed no page ever scrolls sideways.

Real bugs we found and fixed

  • A CSS mask written like a paint gradient erased the middle of a scrolling row instead of fading its edges. It happened in two separate components before we understood the cause and wrote it into the guide.
  • Closing the document viewer blanked the whole library back to loading bars. We separated "nothing has loaded yet" from "checking for newer data", so a refresh now updates in place instead of looking like a page reload.
  • The filter pills on the Assignments tab sat too close to the list. The spacing rule only matched a direct child, and on that one screen the pills sit inside a wrapper element, so the rule silently did not apply.
  • Colouring every card by status made every screen look the same green, because most students are above the threshold. We changed it so a colour marks identity as a thin rail down the card edge, and status only appears on the badge and the meter.
Say this

"The bugs worth talking about were not crashes — they were things that looked fine in code and wrong on screen. We fixed each one and then wrote the reason into the design guide, so the same mistake could not come back."

Questions you are most likely to be asked

Why Node.js and not Python? Python is standard for AI.

We tried Python first. Our local version was 3.9.1 and the ML libraries were slow and fragile to install. We also decided not to run models ourselves — the AI is called through an API — so Python's ML ecosystem was not actually needed. Node gave us one language across frontend and backend.

Why BM25 instead of embeddings and a vector database?

Embeddings need a model, a vector database and a network call. BM25 is a well-established keyword-ranking algorithm that runs locally with zero API keys, so the assistant works even offline. For a fixed set of college documents with specific terms like subject codes, keyword matching performs well. Embeddings are a planned upgrade, and the retrieval layer is isolated so we can swap it.

How do you stop it from making things up?

Two gates. Retrieval must clear both a score threshold and a term-coverage threshold; if either fails, the answer is "not found in official documents". And any document-based answer must return citations — the document, the section and an excerpt — which the interface displays separately from the answer text.

What happens if the AI API quota runs out during the demo?

It falls back to composing the answer from the retrieved passages directly, and it reports that it has downgraded. We treat a silent downgrade as the worst outcome — answers keep coming, they are just worse, and nobody knows why.

Is the student data real?

No, and deliberately. Real records are private. We wrote a generator that produces realistic demo data in exactly the shape real records take, so a college can substitute its own data without changing any code. The documents the assistant answers from are real public circulars.

How is one student stopped from seeing another's marks?

Every route filters by the identity inside the signed JWT, never by an id in the request body. Even if someone edits the request by hand, the server answers only for the token's owner.

You used AI to write the code. What did you actually do?

We defined the problem, chose the stack and justified it, designed the data model, set the design system, and wrote the constraints the AI had to work inside — the rulebook, the design skill and the agent briefs. Then we reviewed every screen and fixed what was wrong. The engineering judgement is in the decisions and the review, and both are written down in the repo.

What would you do next?

Move retrieval to embeddings for better handling of reworded questions, add support for Gujarati and Hindi queries, and connect to the college's real record system instead of seeded data. All three are listed as known gaps in docs/PROJECT_STATE.md.
